# P0-05 质检结论共享机制

> 子需求ID：P0-05  
> 优先级：P0  
> 状态：待开发  
> 依赖：P0-04 质检执行引擎  
> 被依赖：无（终端模块）

---

## 一、需求概述

### 1.1 功能简介

当多个计划组使用相同质检规则版本并包含相同的游戏+渠道时，共享已有的质检结论，避免重复质检，节省资源成本。

### 1.2 业务价值

- **成本节省**：避免对相同数据重复调用LLM，节省Token消耗
- **效率提升**：复用已有结论，减少质检执行时间
- **一致性保障**：相同数据得到相同的质检结论

---

## 二、功能详情

### 2.1 共享条件

质检结论可被共享需同时满足以下条件：

| 条件 | 说明 |
|------|------|
| 相同质检规则版本 | 两个计划组关联的质检规则集合版本号一致 |
| 相同游戏+渠道 | 两个计划组包含相同的 gameId + channel 组合 |
| 相同数据ID | 两次质检任务抽取的数据中包含相同的 sessionId/dataId |
| 相同质检模式 | 都是会话标注或都是单轮标注 |

### 2.2 缓存Key设计

质检结论缓存的唯一标识由以下字段组成：

```
缓存Key = {ruleVersion}_{gameId}_{channel}_{dataId}_{mode}
```

| 字段 | 说明 | 示例 |
|------|------|------|
| ruleVersion | 质检规则版本号 | v202601101001 |
| gameId | 游戏ID | 1194 |
| channel | 渠道标识 | xy_wxwork |
| dataId | 会话/单轮数据ID | session_12345 |
| mode | 质检模式 | session / single |

### 2.3 共享逻辑流程

```
┌─────────────────────────────────────────────────────────────────────────┐
│                          质检结论共享流程                                 │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   计划组A 执行质检                                                       │
│        │                                                                │
│        ▼                                                                │
│   ┌─────────────┐      ┌─────────────────────────────────────────┐     │
│   │ 获取待质检   │ ───→ │ 查询结论缓存：                            │     │
│   │ 数据列表     │      │ Key = 规则版本 + 游戏 + 渠道 + 数据ID     │     │
│   └─────────────┘      └──────────────┬──────────────────────────┘     │
│                                       │                                 │
│                    ┌──────────────────┴──────────────────┐              │
│                    ▼                                     ▼              │
│             ┌─────────────┐                       ┌─────────────┐       │
│             │  命中缓存    │                       │  未命中缓存  │       │
│             │  直接复用    │                       │  调用LLM质检 │       │
│             │  质检结论    │                       │  并写入缓存  │       │
│             └─────────────┘                       └─────────────┘       │
│                    │                                     │              │
│                    └──────────────┬──────────────────────┘              │
│                                   ▼                                     │
│                          ┌─────────────┐                                │
│                          │  汇总结果    │                                │
│                          │  记录执行    │                                │
│                          └─────────────┘                                │
└─────────────────────────────────────────────────────────────────────────┘
```

### 2.4 共享效果示例

**场景**：两个计划组配置如下

| 计划组 | 质检规则版本 | 游戏渠道 | 抽样数量 |
|--------|-------------|----------|----------|
| 甄选日常质检 | v202601101001 | CFM-微信 | 500条/每游戏 |
| 周末专项质检 | v202601101001 | CFM-微信 | 300条/每游戏 |

**执行结果**：

1. 「甄选日常质检」先执行，对 CFM-微信 的 500 条数据完成质检，结论写入缓存
2. 「周末专项质检」后执行，对 CFM-微信 抽取 300 条数据时：
   - 若 300 条数据全部在之前 500 条中 → **直接复用**，0 次 LLM 调用
   - 若 200 条在之前 500 条中，100 条是新数据 → **复用 200 条 + 新质检 100 条**

**成本节省**：避免对相同数据重复调用 LLM，节省 Token 消耗。

### 2.5 缓存失效规则

| 场景 | 处理方式 |
|------|----------|
| 质检规则版本更新 | 旧版本缓存失效，需重新质检 |
| 手动触发"全量重跑" | 忽略缓存，强制重新质检并更新缓存 |
| 缓存过期 | 支持配置缓存有效期（默认7天），过期后自动清理 |

### 2.6 界面展示

在执行记录中展示缓存命中情况：

| 字段 | 说明 | 展示要求 | 案例 |
|------|------|----------|------|
| 总任务数 | 本次需要质检的数据条数 | 数字 | 500 |
| 缓存命中 | 复用已有质检结论的条数 | 数字 + 百分比 | 150 (30%) |
| 实际质检 | 实际调用 LLM 的条数 | 数字 | 350 |
| 节省Token | 因缓存命中节省的预估 Token 数 | 数字 | 约45,000 |

## 三、数据模型

### 3.1 质检结论缓存（InspectionResultCache）

```typescript
interface InspectionResultCache {
  id: string
  cacheKey: string              // 缓存Key
  ruleVersion: string           // 质检规则版本
  gameId: string                // 游戏ID
  channel: string               // 渠道
  dataId: string                // 数据ID
  mode: 'session' | 'single'    // 质检模式
  result: InspectionResult      // 质检结论
  createdAt: string             // 创建时间
  expireAt: string              // 过期时间
  hitCount: number              // 命中次数
}
```

### 3.2 质检结论（InspectionResult）

```typescript
interface InspectionResult {
  conclusion: 'excellent' | 'qualified' | 'unqualified' | 'risk'  // 质检结论
  score?: number                // 评分
  issues: Issue[]               // 问题列表
  rawResponse?: string          // LLM原始响应
}

interface Issue {
  code: string                  // 错误码
  category: string              // 大类
  subcategory: string           // 小类
  description: string           // 问题描述
  severity: 'high' | 'medium' | 'low'
}
```

### 3.3 缓存配置（CacheConfig）

```typescript
interface CacheConfig {
  enabled: boolean              // 是否启用缓存
  ttl: number                   // 缓存有效期（天）
  maxSize?: number              // 最大缓存条目数
}
```

## 四、接口设计

### 4.1 查询缓存

```
POST /api/inspection-cache/query
```

**请求体**：
```json
{
  "ruleVersion": "string",
  "gameId": "string",
  "channel": "string",
  "dataIds": ["string"],
  "mode": "session"
}
```

**响应**：
```json
{
  "hits": [
    {
      "dataId": "string",
      "result": { ... }
    }
  ],
  "misses": ["string"]
}
```

### 4.2 写入缓存

```
POST /api/inspection-cache/write
```

**请求体**：
```json
{
  "ruleVersion": "string",
  "gameId": "string",
  "channel": "string",
  "mode": "session",
  "results": [
    {
      "dataId": "string",
      "result": { ... }
    }
  ]
}
```

### 4.3 清理缓存

```
DELETE /api/inspection-cache
```

**查询参数**：
- `ruleVersion`: 清理指定版本的缓存
- `expired`: 仅清理过期缓存

### 4.4 获取缓存统计

```
GET /api/inspection-cache/stats
```

**响应**：
```json
{
  "totalCount": 10000,
  "hitRate": 0.35,
  "tokenSaved": 1500000,
  "storageSize": "50MB"
}
```
