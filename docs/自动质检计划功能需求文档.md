## 一、需求概述

### 1.1 背景与目的

1. **配置效率低**：当前自动质检配置主要由算法和工程同学在后台进行，产品/运营人员无法及时调整质检规则、优化质检效果。

2. **异常处理链路长**：遇到线上服务量大或资源不足的情况时，质检流程易报错异常，目前"发现 → 反馈 → 处理"的闭环链路长，且处理人力紧缺，影响统计周期的数据完整性。

### 1.2 核心目标

| 目标 | 说明 |
|------|------|
| **平台质检配置完善** | 支持产品/运营人员配置质检计划、数据过滤规则、执行周期等，实现全流程产品/运营可参与 |
| **运维保障** | 通过监控和企微告警机制，确保质检任务的稳定运行，及时发现和处理服务异常 |
| **多维度管理** | 支持按计划组、游戏、渠道等多维度查看和管理质检任务 |

## 三、详细功能需求

### 3.1 计划组管理

**功能目标**：通过"计划组"批量管理多个游戏+渠道的质检任务，实现统一配置、统一监控。

#### 3.1.1 计划组配置项详细说明

新建/编辑计划组时，配置弹窗分为以下几个区域：

---

**一、基本信息**

| 配置项 | 字段名 | 类型 | 必填 | 默认值 | 说明 |
|--------|--------|------|------|--------|------|
| 计划组名称 | name | 文本输入 | ✅ | - | 唯一标识名称，例如："甄选日常质检计划"，最多50字 |
| 描述 | description | 多行文本 | ❌ | - | 对计划组用途的补充说明，最多200字 |
| 关联质检规则 | ruleVersion | 下拉选择 | ✅ | 最新版本 | 选择已发布的质检规则版本，用于质检结论共享判断 |
| 启用状态 | enabled | 开关 | ✅ | 开启 | 控制计划组是否参与定时执行 |

---

**二、执行计划配置**

| 配置项 | 字段名 | 类型 | 必填 | 可选值 | 默认值 | 说明 |
|--------|--------|------|------|--------|--------|------|
| 执行周期 | cycle | 下拉选择 | ✅ | 每天 / 每周 / 自定义 | 每天 | 定义任务执行频率 |
| 执行时间 | executeTime | 时间选择器 | ✅ | 00:00~23:59 | 09:00 | 精确到分钟 |
| 周几执行 | weekDays | 多选复选框 | 条件必填 | 周一~周日 | 周一 | 仅"每周"模式下显示且必填 |
| 质检模式 | mode | 下拉选择 | ✅ | 会话标注 / 单轮标注 | 会话标注 | 定义质检颗粒度 |
| 质检数据范围 | dataRange | 下拉选择 | ✅ | T-1日 / T-2日 / 自定义 | T-1日 | 指定质检的数据时间范围 |

**执行周期详细说明：**

| 周期类型 | 字段值 | 执行逻辑 | 配置示例 |
|----------|--------|----------|----------|
| 每天 | daily | 每天固定时间执行 | 每天 09:00 执行 |
| 每周 | weekly | 每周指定几天执行 | 每周一、三、五 09:00 执行 |
| 自定义 | custom | Cron表达式（高级） | `0 9 * * 1-5` 表示周一到周五9点执行 |

**质检模式详细说明：**

| 模式 | 字段值 | 质检粒度 | 适用场景 | Token消耗 |
|------|--------|----------|----------|-----------|
| 单轮标注 | single | 一问一答 | 知识准确性校验、敏感词检测、回复规范检查 | 较低 |
| 会话标注 | session | 整场Session | 上下文逻辑一致性、服务态度评估、问题解决判断 | 较高 |

---

**三、抽样配置**

| 配置项 | 字段名 | 类型 | 必填 | 可选值 | 默认值 | 说明 |
|--------|--------|------|------|--------|--------|------|
| 抽样方式 | samplingMethod | 下拉选择 | ✅ | 随机抽样 / 最新优先 / 全量 | 随机抽样 | 定义数据选取逻辑 |
| 抽样数量 | maxCount | 数字输入 | ✅ | 1~10000 | 500 | 单位：条 |
| 抽样范围 | samplingScope | 下拉选择 | ✅ | 每个游戏抽取该数量 / 所有游戏共抽取该数量 | 每个游戏 | 定义抽样维度 |

**抽样方式详细说明：**

| 抽样方式 | 字段值 | 逻辑说明 | 适用场景 |
|----------|--------|----------|----------|
| 随机抽样 | random | 从符合条件的数据中随机选取 | 日常质检，保证样本分布均匀 |
| 最新优先 | latest | 按时间倒序选取最新数据 | 关注近期数据质量 |
| 全量 | all | 对所有符合条件的数据质检 | 专项全量检查（注意资源消耗） |

**抽样范围详细说明：**

| 选项 | 字段值 | 逻辑 | 示例 |
|------|--------|------|------|
| 每个游戏抽取该数量 | perGame | 每个游戏独立抽样 | 配置500条，3个游戏则共抽取1500条 |
| 所有游戏共抽取该数量 | total | 所有游戏合计抽样，按各游戏数据量比例分配 | 配置500条，3个游戏共抽取500条 |

---

**四、数据过滤规则**

| 配置项 | 字段名 | 类型 | 必填 | 默认值 | 说明 |
|--------|--------|------|------|--------|------|
| 过滤纯Bot会话 | filter.excludePureBot | 开关 | ❌ | 开启 | 过滤仅Bot推送消息且用户未回复的会话 |
| 过滤用户未回复 | filter.excludeNoReply | 开关 | ❌ | 开启 | 过滤用户无任何回复的会话 |
| 黑名单关键词 | filter.blacklistKeywords | 标签输入 | ❌ | [] | 命中关键词的会话/单轮直接跳过，如："测试","忽略","test" |
| 最小消息数 | filter.minMessages | 数字输入 | ❌ | 1 | 会话消息数低于此值则过滤 |
| 最大消息数 | filter.maxMessages | 数字输入 | ❌ | 不限 | 会话消息数高于此值则过滤 |

**过滤规则逻辑：**
- 多个过滤条件为 **AND** 关系，需同时满足才会被过滤
- 过滤在抽样之前执行，先过滤再抽样
- 被过滤的数据不消耗 Token

**五、监控配置**

| 配置项 | 字段名 | 类型 | 必填 | 默认值 | 说明 |
|--------|--------|------|------|--------|------|
| 启用监控 | monitoring.enabled | 开关 | ❌ | 开启 | 是否启用异常监控 |

**监控指标配置：**

| 监控项 | 字段名 | 类型 | 阈值含义 | 默认阈值 | 说明 |
|--------|--------|------|----------|----------|------|
| 缺数据监控 | monitoring.metrics.dataMissing | 开关 + 数字 | 连续N次无数据 | 3次 | 数据源无可采集数据时告警 |
| 模型报错监控 | monitoring.metrics.modelError | 开关 + 数字 | 错误率 > N% | 10% | LLM服务报错、Token超限、API超时 |
| 资源不足监控 | monitoring.metrics.resourceInsufficient | 开关 + 数字 | 堆积 > N条 | 1000条 | 任务队列积压严重 |
| 进度异常监控 | monitoring.metrics.progressAbnormal | 开关 + 数字 | 预计超时N小时 | 2小时 | 执行时间异常过长 |

---

**六、告警配置**

| 配置项 | 字段名 | 类型 | 必填 | 默认值 | 说明 |
|--------|--------|------|------|--------|------|
| 启用告警 | alert.enabled | 开关 | ❌ | 开启 | 是否启用异常告警通知 |

**告警渠道配置：**

| 渠道 | 字段名 | 类型 | 说明 |
|------|--------|------|------|
| 企业微信机器人 | alert.channels.wechat.enabled | 开关 | 是否启用企微群机器人告警 |
| Webhook地址 | alert.channels.wechat.webhookUrl | 文本输入 | 企微机器人的Webhook URL |
| 邮件通知 | alert.channels.email.enabled | 开关 | 是否启用邮件告警 |

**告警接收人配置：**

| 配置项 | 字段名 | 类型 | 格式 | 示例 |
|--------|--------|------|------|------|
| 接收人列表 | alert.receivers | 标签输入 | rtx(姓名) | xiaohuwang(王小虎) |
| 邮箱 | - | 自动生成 | {rtx}@tencent.com | xiaohuwang@tencent.com |

**告警触发条件：**
- 任务整体失败
- 单次任务失败率超过监控阈值（如 >10%）
- 资源异常（可用Token余额不足等）
- 连续N次缺数据

#### 3.1.2 计划组列表展示

**字段明细：**

| 字段名称 | 说明 | 展示要求 | 案例 |
|----------|------|----------|------|
| 计划组名称 | 计划组的唯一标识名称 | 支持点击展开/收起子列表，名称过长时省略显示并悬浮展示全文 | 甄选日常质检计划 |
| 状态 | 计划组当前运行状态 | 彩色状态标签：🟢正常、🔵执行中、🔴异常、⚪已停用 | 🟢 正常 |
| 游戏渠道数 | 该计划组下关联的游戏渠道数量 | 数字 + "个游戏渠道"文案，点击可展开查看列表 | 3个游戏渠道 |
| 执行周期 | 任务执行频率配置 | 文字描述，周期+时间组合展示 | 每天 09:00 |
| 质检模式 | 会话标注或单轮标注 | 标签形式展示 | [会话标注] |
| 抽样配置 | 抽样数量和范围 | 数量 + 范围文案 | 500条/每游戏 |
| 最近执行 | 最近一次执行的时间 | 时间格式：MM-DD HH:mm，无执行记录显示"-" | 01-16 09:00 |
| 启用开关 | 控制计划组是否启用 | Switch开关组件，开启为蓝色，关闭为灰色 | 🔵开启 / ⚪关闭 |
| 操作 | 更多操作入口 | 下拉菜单按钮"⋯"，点击展开操作列表 | [⋯] |

**状态定义与颜色方案：**

| 状态 | 状态值 | 颜色 | 触发条件 |
|------|--------|------|----------|
| 正常 | normal | 🟢 绿色 | 计划组已启用，无异常，等待下次执行 |
| 执行中 | running | 🔵 蓝色 | 计划组下有任务正在执行 |
| 异常 | error | 🔴 红色 | 计划组下有游戏渠道处于异常状态 |
| 已停用 | stopped | ⚪ 灰色 | 计划组已手动停用 |

**展示规则：**
- 列表默认按创建时间倒序排列，最新创建的在最前
- 异常状态的计划组置顶显示，方便快速处理
- 点击计划组行可展开/收起游戏渠道子列表
- 无数据时显示空状态："暂无计划组，点击右上角按钮创建"

#### 3.1.4 质检结果导出

**功能目标**：支持将质检结果导出为Excel文件，便于离线分析和汇报。

**导出入口：**
- 计划组操作菜单 → "导出质检结果"
- 游戏渠道操作菜单 → "导出质检结果"（导出该游戏渠道的结果）

**导出配置弹窗字段：**

| 配置项 | 字段名 | 类型 | 必填 | 默认值 | 说明 |
|--------|--------|------|------|--------|------|
| 时间范围 | dateRange | 日期范围选择器 | ✅ | 最近7天 | 选择质检执行的时间范围，最大跨度30天 |
| 导出范围 | exportScope | 下拉多选 | ✅ | 全部游戏渠道 | 全部游戏渠道 / 指定游戏渠道（支持多选） |
| 导出内容 | exportContent | 多选复选框 | ✅ | 全选 | 基础信息 / 质检详情 / 异常记录 |

**导出文件说明：**

| 项目 | 说明 | 示例 |
|------|------|------|
| 格式 | Excel文件 | .xlsx |
| 文件名 | {计划组名称}_质检结果_{开始日期}_{结束日期} | 甄选日常质检计划_质检结果_20260110_20260116.xlsx |
| 导出限制 | 单次最多导出10000条记录，超出时提示分批导出 | - |
| 大数据处理 | 数据量>5000条时，后台异步导出，完成后通知用户下载 | - |

**导出Excel字段说明（Sheet1：质检明细）：**

| 字段名称 | 说明 | 展示要求 | 案例 |
|----------|------|----------|------|
| 会话ID | 会话唯一标识 | 文本格式，保持原始ID | cfm_20260115_093000_001 |
| 游戏名称 | 游戏中文名 | 文本 | 穿越火线 |
| 渠道名称 | 渠道中文名 | 文本 | 微信 |
| 质检时间 | 质检执行时间 | YYYY-MM-DD HH:mm:ss | 2026-01-15 09:30:00 |
| 质检结果 | 质检结论 | 文本：优秀/合格/不合格/风险 | 合格 |
| 质检评分 | 综合评分 | 数字，保留1位小数 | 85.5 |
| 问题数量 | 发现的问题项数量 | 数字 | 2 |
| 问题详情 | 具体问题描述 | 多个问题用换行分隔 | 1.[#11041]服务主动性-推荐内容与用户咨询无关 |
| 对话内容 | 完整对话记录 | 保持时间戳和角色标识 | 2026-01-15 09:28:00 玩家：xxx... |

**交互说明：**
- 点击"导出"按钮后，若数据量≤5000条，直接下载文件
- 若数据量>5000条，显示提示："数据量较大，已提交后台处理，完成后将通过消息通知您下载"
- 导出过程中按钮显示loading状态，禁止重复点击

#### 3.1.5 历史质检记录查看

**功能目标**：查看计划组下所有游戏渠道的历史执行记录，支持筛选和详情查看。

**入口方式：**
1. 计划组行操作菜单 → "查看历史记录" → 弹出历史记录弹窗
2. 点击游戏渠道行的"最近执行"时间链接 → 弹出该游戏渠道的执行详情
3. 计划组展开后，游戏渠道列表下方显示"执行记录"Tab区域

**历史记录列表字段：**

### 3.3 质检结论共享机制（去重优化）

**功能目标**：当多个计划组使用相同质检规则版本并包含相同的游戏+渠道时，共享已有的质检结论，避免重复质检，节省资源成本。

#### 3.3.1 共享条件

质检结论可被共享需同时满足以下条件：

| 条件 | 说明 |
|------|------|
| 相同质检规则版本 | 两个计划组关联的质检规则集合版本号一致 |
| 相同游戏+渠道 | 两个计划组包含相同的 gameId + channel 组合 |
| 相同数据范围 | 质检的数据时间范围有重叠（如都是T-1日数据） |
| 相同质检模式 | 都是会话标注或都是单轮标注 |

#### 3.3.2 共享逻辑

```
┌─────────────────────────────────────────────────────────────────────────┐
│                          质检结论共享流程                                 │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   计划组A 执行质检                                                       │
│        │                                                                │
│        ▼                                                                │
│   ┌─────────────┐      ┌─────────────────────────────────────────┐     │
│   │ 获取待质检   │ ───→ │ 查询结论缓存：                            │     │
│   │ 数据列表     │      │ Key = 规则版本 + 游戏 + 渠道 + 数据ID     │     │
│   └─────────────┘      └──────────────┬──────────────────────────┘     │
│                                       │                                 │
│                    ┌──────────────────┴──────────────────┐              │
│                    ▼                                     ▼              │
│             ┌─────────────┐                       ┌─────────────┐       │
│             │  命中缓存    │                       │  未命中缓存  │       │
│             │  直接复用    │                       │  调用LLM质检 │       │
│             │  质检结论    │                       │  并写入缓存  │       │
│             └─────────────┘                       └─────────────┘       │
│                    │                                     │              │
│                    └──────────────┬──────────────────────┘              │
│                                   ▼                                     │
│                          ┌─────────────┐                                │
│                          │  汇总结果    │                                │
│                          │  记录执行    │                                │
│                          └─────────────┘                                │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 3.3.3 缓存Key设计

质检结论缓存的唯一标识由以下字段组成：

```
缓存Key = {ruleVersion}_{gameId}_{channel}_{dataId}_{mode}
```

| 字段 | 说明 | 示例 |
|------|------|------|
| ruleVersion | 质检规则版本号 | v2.1.0 |
| gameId | 游戏ID | CFM |
| channel | 渠道标识 | weixin |
| dataId | 会话/单轮数据ID | session_12345 |
| mode | 质检模式 | session / single |

#### 3.3.4 共享效果示例

**场景**：两个计划组配置如下

| 计划组 | 质检规则版本 | 游戏渠道 | 抽样数量 |
|--------|-------------|----------|----------|
| 甄选日常质检 | v2.1.0 | CFM-微信、DNF-QQ | 500条/每游戏 |
| 周末专项质检 | v2.1.0 | CFM-微信、LOL-微信 | 300条/每游戏 |

**执行结果**：

1. 「甄选日常质检」先执行，对 CFM-微信 的 500 条数据完成质检，结论写入缓存
2. 「周末专项质检」后执行，对 CFM-微信 抽取 300 条数据时：
   - 若 300 条数据全部在之前 500 条中 → **直接复用**，0 次 LLM 调用
   - 若 200 条在之前 500 条中，100 条是新数据 → **复用 200 条 + 新质检 100 条**

**成本节省**：避免对相同数据重复调用 LLM，节省 Token 消耗。

#### 3.3.5 缓存失效规则

| 场景 | 处理方式 |
|------|----------|
| 质检规则版本更新 | 旧版本缓存失效，需重新质检 |
| 手动触发"全量重跑" | 忽略缓存，强制重新质检并更新缓存 |
| 缓存过期 | 支持配置缓存有效期（默认7天），过期后自动清理 |

#### 3.3.6 界面展示

在执行记录中展示缓存命中情况：

| 字段 | 说明 |
|------|------|
| 总任务数 | 本次需要质检的数据条数 |
| 缓存命中 | 复用已有质检结论的条数 |
| 实际质检 | 实际调用 LLM 的条数 |
| 节省Token | 因缓存命中节省的预估 Token 数 |

#### 3.6.4 重试与恢复

**自动重试机制：**

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| 最大重试次数 | 自动重试的最大次数 | 3次 |
| 重试间隔 | 每次重试之间的等待时间 | 30秒 |
| 可重试错误类型 | 哪些错误类型会触发自动重试 | 网络超时、服务暂时不可用 |

**手动重跑操作：**

| 操作 | 字段值 | 说明 | 入口 | 交互细节 |
|------|--------|------|------|----------|
| 重跑失败项 | retryFailed | 仅重新执行失败的数据条目 | 操作菜单、异常详情弹窗 | 确认弹窗："确定重跑失败的50条数据？" |
| 全量重跑 | retryAll | 重新执行所有任务，忽略缓存 | 操作菜单、异常详情弹窗 | 确认弹窗："确定全量重跑？将忽略缓存重新质检所有数据" |

**重跑执行逻辑：**
- 重跑失败项：仅将失败的数据条目放入队列，不影响已成功数据
- 全量重跑：忽略缓存，强制重新质检所有数据并更新缓存
- 新增执行记录，标记执行模式（retryFailed / retryAll）
- 重跑任务进入队列后，状态变为"排队中"

**重跑记录标识：**

| 字段名称 | 说明 | 展示要求 | 案例 |
|----------|------|----------|------|
| 执行模式 | 区分定时/手动/重跑 | 标签形式 | [定时] [手动] [重跑失败] [全量重跑] |
| 关联执行ID | 重跑任务关联的原执行记录ID | 可点击跳转 | 关联：exec_20260115_001 |

## 四、质检规则大小类定义说明

**功能目标**：为质检规则的大类和小类添加定义说明，**为自动质检模型提供分类判断依据**。模型在执行质检时，根据定义说明判断当前会话/消息应归属哪个分类，类似于场景分类的规则索引。

**核心价值**：
- **模型分类依据**：定义说明作为Prompt的一部分传入LLM，指导模型识别和分类质检问题
- **规则匹配参考**：告诉模型各分类的适用场景、触发条件和典型特征
- **结果一致性保障**：明确的定义说明可提升模型输出的一致性和准确性

**页面路径**：`质检中心 > 质检标准配置`

### 4.1 定义说明字段

## 六、数据结构定义

### 6.1 计划组（PlanGroup）

```typescript
interface PlanGroup {
  id: string                    // 计划组唯一标识
  name: string                  // 计划组名称
  description?: string          // 描述
  enabled: boolean              // 是否启用
  ruleVersion: string           // 关联的质检规则版本号（用于结论共享判断）
  cycle: 'daily' | 'weekly' | 'custom'  // 执行周期
  executeTime: string           // 执行时间
  weekDays?: number[]           // 周几执行
  mode: 'session' | 'single'    // 质检模式
  maxCount: number              // 抽样数量
  samplingScope: 'total' | 'perGame'    // 抽样范围
  samplingMethod: 'random' | 'latest' | 'all'  // 抽样方式
  filter: FilterConfig          // 过滤规则
  monitoring: MonitoringConfig  // 监控配置
  alert: AlertConfig            // 告警配置
  gameChannels: GameChannelItem[]  // 游戏渠道列表
  createdAt: string
  updatedAt: string
}
```

### 6.2 游戏渠道项（GameChannelItem）

```typescript
interface GameChannelItem {
  id: string
  gameId: string
  gameName: string
  channel: string
  channelName: string
  enabled: boolean
  status: 'running' | 'normal' | 'error' | 'stopped'
  errorInfo?: ErrorInfo         // 异常信息
  executions: ExecutionRecord[] // 执行记录
}
```

### 6.3 异常信息（ErrorInfo）

```typescript
interface ErrorInfo {
  type: 'dataMissing' | 'modelError' | 'resourceInsufficient' | 'progressAbnormal' | 'executionFailed'
  message: string       // 异常摘要
  detail?: string       // 异常详情
  occurredAt: string    // 发生时间
  resolvedAt?: string   // 解决时间
}
```

### 6.4 执行记录（ExecutionRecord）

```typescript
interface ExecutionRecord {
  id: string
  time: string
  total: number             // 总任务数
  completed: number         // 完成数
  failed: number            // 失败数
  hasError: number          // 异常数
  cacheHit: number          // 缓存命中数（复用已有质检结论）
  actualInspected: number   // 实际质检数（调用LLM）
  tokenSaved?: number       // 节省的Token数（预估）
  status: 'completed' | 'running' | 'error'
  mode?: 'all' | 'failed'   // 执行模式
  errorMessage?: string
}
```

### 6.5 监控配置（MonitoringConfig）

```typescript
interface MonitoringConfig {
  enabled: boolean
  metrics: {
    dataMissing: { enabled: boolean; threshold: number }
    modelError: { enabled: boolean; threshold: number }
    resourceInsufficient: { enabled: boolean; threshold: number }
    progressAbnormal: { enabled: boolean; threshold: number }
  }
}
```

### 6.6 告警配置（AlertConfig）

```typescript
interface AlertConfig {
  enabled: boolean
  channels: {
    wechat: { enabled: boolean; webhookUrl: string }
    email: { enabled: boolean; recipients: string[] }
  }
  receivers: { rtx: string; name: string }[]
}
```
