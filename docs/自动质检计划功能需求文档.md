> 版本：v1.0  
> 更新日期：2026-01-16  
> 页面路径：`/auto-quality-inspection`

---

## 一、需求概述

### 1.1 背景与目的

1. **配置效率低**：当前自动质检配置主要由算法和工程同学在后台进行，产品/运营人员无法及时调整质检规则、优化质检效果。

2. **异常处理链路长**：遇到线上服务量大或资源不足的情况时，质检流程易报错异常，目前"发现 → 反馈 → 处理"的闭环链路长，且处理人力紧缺，影响统计周期的数据完整性。

### 1.2 核心目标

| 目标 | 说明 |
|------|------|
| **平台质检配置完善** | 支持产品/运营人员配置质检计划、数据过滤规则、执行周期等，实现全流程产品/运营可参与 |
| **运维保障** | 通过监控和企微告警机制，确保质检任务的稳定运行，及时发现和处理服务异常 |
| **多维度管理** | 支持按计划组、游戏、渠道等多维度查看和管理质检任务 |

## 三、详细功能需求

### 3.1 计划组管理

**功能目标**：通过"计划组"批量管理多个游戏+渠道的质检任务，实现统一配置、统一监控。

#### 3.1.1 计划组配置界面

**基本信息**

| 配置项 | 类型 | 说明 |
|--------|------|------|
| 计划组名称 | 文本输入 | 必填，例如："甄选日常质检计划" |
| 描述 | 文本输入 | 可选，对计划组的补充说明 |
| 启用状态 | 开关 | 控制计划组是否参与定时执行 |

**执行配置**

| 配置项 | 类型 | 可选值 | 说明 |
|--------|------|--------|------|
| 执行周期 | 下拉选择 | 每天 / 每周 / 自定义 | 定义任务执行频率 |
| 执行时间 | 时间选择器 | - | 例如：09:00 |
| 周几执行 | 多选 | 周一~周日 | 仅"每周"模式下显示 |
| 质检模式 | 下拉选择 | 会话标注 / 单轮标注 | 定义质检颗粒度 |

**质检模式说明：**

| 模式 | 说明 | 适用场景 |
|------|------|----------|
| 单轮标注 | 针对"一问一答"进行独立校验 | 知识准确性校验、敏感词检测 |
| 会话标注 | 针对整场Session进行校验 | 上下文逻辑一致性、服务态度、是否解决问题 |

#### 3.1.2 计划组操作

| 操作 | 入口 | 说明 |
|------|------|------|
| 新建 | 页面右上角"新建计划组"按钮 | 弹窗表单创建 |
| 编辑 | 计划组行操作菜单"编辑配置" | 修改所有配置项 |
| 删除 | 计划组行操作菜单"删除计划组" | 需二次确认，删除后关联的游戏渠道配置同步删除 |
| 启用/停用 | 计划组行Switch开关 | 实时切换启用状态 |

### 3.2 数据过滤与抽样（成本控制）

**功能目标**：通过多维度的清洗和抽样，精准筛选高价值数据，避免资源浪费。

#### 3.2.1 基础清洗规则（黑名单与去噪）

**角色交互过滤**

| 规则 | 配置项 | 说明 |
|------|--------|------|
| 过滤纯Bot会话 | 复选框 | 过滤掉"仅Bot推送消息且用户未回复"的会话，此类数据无质检价值 |
| 过滤用户未回复 | 复选框 | 过滤掉用户无交互的会话，例如运营推送活动场景 |

**关键词黑名单**

| 配置项 | 类型 | 说明 |
|--------|------|------|
| 黑名单关键词 | 标签输入 | 支持添加/删除，如："测试"、"忽略"、"test" |
| 匹配逻辑 | - | 命中黑名单关键词的会话/单轮，直接跳过，不消耗Token |

**消息数量过滤**

| 配置项 | 类型 | 说明 |
|--------|------|------|
| 最小消息数 | 数字输入 | 会话消息数低于此值则过滤 |
| 最大消息数 | 数字输入 | 会话消息数高于此值则过滤 |

#### 3.2.2 抽样与限流策略

| 配置项 | 类型 | 可选值 | 说明 |
|--------|------|--------|------|
| 抽样方式 | 下拉选择 | 随机抽样 / 最新优先 / 全量 | 定义数据选取逻辑 |
| 抽样数量 | 数字输入 | - | 最大质检条数，例如：500条 |
| **抽样范围** | 下拉选择 | 每个游戏抽取该数量 / 所有游戏共抽取该数量 | **新增**：定义抽样维度 |

**抽样范围说明：**

| 选项 | 逻辑 | 示例 |
|------|------|------|
| 每个游戏抽取该数量 | 每个游戏独立抽样 | 配置500条，3个游戏则共抽取1500条 |
| 所有游戏共抽取该数量 | 所有游戏合计抽样 | 配置500条，3个游戏共抽取500条 |

### 3.3 质检结论共享机制（去重优化）

**功能目标**：当多个计划组使用相同质检规则版本并包含相同的游戏+渠道时，共享已有的质检结论，避免重复质检，节省资源成本。

#### 3.3.1 共享条件

质检结论可被共享需同时满足以下条件：

| 条件 | 说明 |
|------|------|
| 相同质检规则版本 | 两个计划组关联的质检规则集合版本号一致 |
| 相同游戏+渠道 | 两个计划组包含相同的 gameId + channel 组合 |
| 相同数据范围 | 质检的数据时间范围有重叠（如都是T-1日数据） |
| 相同质检模式 | 都是会话标注或都是单轮标注 |

#### 3.3.2 共享逻辑

```
┌─────────────────────────────────────────────────────────────────────────┐
│                          质检结论共享流程                                 │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   计划组A 执行质检                                                       │
│        │                                                                │
│        ▼                                                                │
│   ┌─────────────┐      ┌─────────────────────────────────────────┐     │
│   │ 获取待质检   │ ───→ │ 查询结论缓存：                            │     │
│   │ 数据列表     │      │ Key = 规则版本 + 游戏 + 渠道 + 数据ID     │     │
│   └─────────────┘      └──────────────┬──────────────────────────┘     │
│                                       │                                 │
│                    ┌──────────────────┴──────────────────┐              │
│                    ▼                                     ▼              │
│             ┌─────────────┐                       ┌─────────────┐       │
│             │  命中缓存    │                       │  未命中缓存  │       │
│             │  直接复用    │                       │  调用LLM质检 │       │
│             │  质检结论    │                       │  并写入缓存  │       │
│             └─────────────┘                       └─────────────┘       │
│                    │                                     │              │
│                    └──────────────┬──────────────────────┘              │
│                                   ▼                                     │
│                          ┌─────────────┐                                │
│                          │  汇总结果    │                                │
│                          │  记录执行    │                                │
│                          └─────────────┘                                │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 3.3.3 缓存Key设计

质检结论缓存的唯一标识由以下字段组成：

```
缓存Key = {ruleVersion}_{gameId}_{channel}_{dataId}_{mode}
```

| 字段 | 说明 | 示例 |
|------|------|------|
| ruleVersion | 质检规则版本号 | v2.1.0 |
| gameId | 游戏ID | CFM |
| channel | 渠道标识 | weixin |
| dataId | 会话/单轮数据ID | session_12345 |
| mode | 质检模式 | session / single |

#### 3.3.4 共享效果示例

**场景**：两个计划组配置如下

| 计划组 | 质检规则版本 | 游戏渠道 | 抽样数量 |
|--------|-------------|----------|----------|
| 甄选日常质检 | v2.1.0 | CFM-微信、DNF-QQ | 500条/每游戏 |
| 周末专项质检 | v2.1.0 | CFM-微信、LOL-微信 | 300条/每游戏 |

**执行结果**：

1. 「甄选日常质检」先执行，对 CFM-微信 的 500 条数据完成质检，结论写入缓存
2. 「周末专项质检」后执行，对 CFM-微信 抽取 300 条数据时：
   - 若 300 条数据全部在之前 500 条中 → **直接复用**，0 次 LLM 调用
   - 若 200 条在之前 500 条中，100 条是新数据 → **复用 200 条 + 新质检 100 条**

**成本节省**：避免对相同数据重复调用 LLM，节省 Token 消耗。

#### 3.3.5 缓存失效规则

| 场景 | 处理方式 |
|------|----------|
| 质检规则版本更新 | 旧版本缓存失效，需重新质检 |
| 手动触发"全量重跑" | 忽略缓存，强制重新质检并更新缓存 |
| 缓存过期 | 支持配置缓存有效期（默认7天），过期后自动清理 |

#### 3.3.6 界面展示

在执行记录中展示缓存命中情况：

| 字段 | 说明 |
|------|------|
| 总任务数 | 本次需要质检的数据条数 |
| 缓存命中 | 复用已有质检结论的条数 |
| 实际质检 | 实际调用 LLM 的条数 |
| 节省Token | 因缓存命中节省的预估 Token 数 |

### 3.4 游戏渠道管理

**功能目标**：管理计划组下关联的游戏+渠道组合，支持独立启停控制。

#### 3.4.1 游戏渠道配置

| 操作 | 入口 | 说明 |

| 异常 | 红色 | 发生错误，需处理 |

### 3.6 任务监控与告警配置

**功能目标**：对质检任务的运行状态进行全链路监控，确保异常及时被发现和处理。

#### 3.6.1 异常监控指标

系统需监控以下异常状态，并记录日志：

| 监控项 | 类型 | 阈值配置 | 说明 |
|--------|------|----------|------|
| 缺数据监控 | 任务级 | 连续N次无数据 | 数据源无可采集数据 |
| 模型报错监控 | 条目级 | 错误率 > N% | LLM服务报错（500/502）、Token超限、API超时 |
| 资源不足监控 | 系统级 | 堆积 > N条 | 任务队列积压严重 |
| 进度异常监控 | 任务级 | 预计超时N小时 | 执行时间异常过长 |

#### 3.6.2 告警通知机制

**告警渠道配置：**

| 渠道 | 配置项 | 说明 |
|------|--------|------|
| 企业微信群机器人 | Webhook URL | 输入企微机器人的URL |
| 邮件通知 | - | 发送至接收人的企业邮箱 |

**告警接收人配置：**

| 配置项 | 格式 | 说明 |
|--------|------|------|
| 接收人 | rtx(姓名) | 例如：xiaohuwang(王小虎) |
| 邮箱 | 自动生成 | {rtx}@tencent.com |

**告警触发条件：**

- 任务整体失败
- 单次任务失败率超过监控阈值
- 资源异常（可用Token余额不足等）

**告警模板示例：**

```
⚠️ [自动质检] 任务执行异常

计划组名称：甄选日常质检计划
游戏渠道：地下城与勇士 - QQ
失败原因：LLM服务响应超时 (Timeout)
失败数量：50/500
时间：2026-01-15 10:30:00

请 @王小虎 @张三 及时处理。
```

#### 3.6.3 异常详情查看

**入口**：状态为"异常"时，显示"查看"链接

**异常详情弹窗内容：**

| 区域 | 内容 |
|------|------|
| 基本信息 | 计划组名称、游戏渠道名称 |
| 异常信息 | 异常类型标签、发生时间、摘要信息、详细信息（预格式化） |
| 执行记录 | 最近5次执行记录表格（时间、状态、完成/失败/异常数） |
| 操作按钮 | 重跑失败任务、全量重跑、关闭 |

**异常类型标签：**

| 类型 | 标签 | 颜色 |
|------|------|------|
| dataMissing | 缺数据 | 橙色 |
| modelError | 模型报错 | 红色 |
| resourceInsufficient | 资源不足 | 黄色 |
| progressAbnormal | 进度异常 | 紫色 |
| executionFailed | 执行失败 | 红色 |

#### 3.6.4 重试与恢复

**自动重试：**
- 针对网络波动或超时导致的失败，系统自动重试3次（间隔可配置）

**手动重跑：**

| 模式 | 说明 | 入口 |
|------|------|------|
| 全量重跑 | 重新执行所有任务 | 操作菜单、异常详情弹窗 |
| 重跑失败项 | 仅重新执行失败的数据条目 | 操作菜单、异常详情弹窗 |

**重跑逻辑：**
- 仅重新把失败的数据条目放入队列
- 不重复跑已成功的数据，节省成本
- 新增执行记录，标记执行模式（all/failed）

## 五、数据结构定义

### 5.1 计划组（PlanGroup）

```typescript
interface PlanGroup {
  id: string                    // 计划组唯一标识
  name: string                  // 计划组名称
  description?: string          // 描述
  enabled: boolean              // 是否启用
  ruleVersion: string           // 关联的质检规则版本号（用于结论共享判断）
  cycle: 'daily' | 'weekly' | 'custom'  // 执行周期
  executeTime: string           // 执行时间
  weekDays?: number[]           // 周几执行
  mode: 'session' | 'single'    // 质检模式
  maxCount: number              // 抽样数量
  samplingScope: 'total' | 'perGame'    // 抽样范围
  samplingMethod: 'random' | 'latest' | 'all'  // 抽样方式
  filter: FilterConfig          // 过滤规则
  monitoring: MonitoringConfig  // 监控配置
  alert: AlertConfig            // 告警配置
  gameChannels: GameChannelItem[]  // 游戏渠道列表
  createdAt: string
  updatedAt: string
}
```

### 5.2 游戏渠道项（GameChannelItem）

```typescript
interface GameChannelItem {
  id: string
  gameId: string
  gameName: string
  channel: string
  channelName: string
  enabled: boolean
  status: 'running' | 'normal' | 'error' | 'stopped'
  errorInfo?: ErrorInfo         // 异常信息
  executions: ExecutionRecord[] // 执行记录
}
```

### 5.3 异常信息（ErrorInfo）

```typescript
interface ErrorInfo {
  type: 'dataMissing' | 'modelError' | 'resourceInsufficient' | 'progressAbnormal' | 'executionFailed'
  message: string       // 异常摘要
  detail?: string       // 异常详情
  occurredAt: string    // 发生时间
  resolvedAt?: string   // 解决时间
}
```

### 5.4 执行记录（ExecutionRecord）

```typescript
interface ExecutionRecord {
  id: string
  time: string
  total: number             // 总任务数
  completed: number         // 完成数
  failed: number            // 失败数
  hasError: number          // 异常数
  cacheHit: number          // 缓存命中数（复用已有质检结论）
  actualInspected: number   // 实际质检数（调用LLM）
  tokenSaved?: number       // 节省的Token数（预估）
  status: 'completed' | 'running' | 'error'
  mode?: 'all' | 'failed'   // 执行模式
  errorMessage?: string
}
```

### 5.5 监控配置（MonitoringConfig）

```typescript
interface MonitoringConfig {
  enabled: boolean
  metrics: {
    dataMissing: { enabled: boolean; threshold: number }
    modelError: { enabled: boolean; threshold: number }
    resourceInsufficient: { enabled: boolean; threshold: number }
    progressAbnormal: { enabled: boolean; threshold: number }
  }
}
```

### 5.6 告警配置（AlertConfig）

```typescript
interface AlertConfig {
  enabled: boolean
  channels: {
    wechat: { enabled: boolean; webhookUrl: string }
    email: { enabled: boolean; recipients: string[] }
  }
  receivers: { rtx: string; name: string }[]
}
```
